# v2.1 Fidelity Review (Phase 1) — findings record

This document records the qualitative fidelity review of bauble's assertion corpus:
for every requirement→assertion link, does the covering assertion exercise the FULL
normative statement? It was done after all class-A assertions carried the auditable
chain (preconditions/stimulus/expected_observables).

Live sources of truth: `bauble coverage` and `bauble audit`. No committed numbers
beyond what this review records qualitatively.

## Method

For each of the 142 covered requirements, the normative text was compared with the
covering assertion's text + stimulus + expected_observables, and where the code
looked narrower than the text, the assertion body was read and its behavior probed
live against both targets (OpenLDAP via podman, 389 DS via podman). Findings were
then classified:

- FULL — the assertion exercises the whole normative statement.
- PARTIAL — the assertion exercises only part; the remainder is a v2.2
  PARTIALLY_COVERED candidate (or already fixed).
- FINDING — the strengthened assertion exposed a genuine server deviation.

## Fidelity fixes applied (this pass)

These assertions were vacuous or narrower than their requirements; all were
strengthened and live-verified:

- `4511.4.12.1` (unrecognized extended request): was "any non-zero", tightened to
  require protocolError (2). Both servers return 2.
- `3062.2.1` (Password Modify): previously verified only that the op returned 0;
  now rebinds with the new password to prove the password actually changed
  (the restore was also reordered so it cannot mask the check).
- `4532.1.1` (Who-Am-I): previously checked resultCode only; now verifies the
  response value is the bound identity (`dn:` authzId) and that the anonymous
  case returns an empty authzId (fresh unbound session).
- `3045.2.1` / `3045.2.2` (vendor info): previously verified single-value only;
  now also attempts a client modify of the attribute and requires rejection
  (NO-USER-MODIFICATION).
- `4527.3.1.1` / `4527.3.2.1` (Pre/Post-Read): previously verified only that the
  update applied; the raw response control was never inspected. Now verifies the
  Pre/Post-Read response control is actually present. Required switching the
  controls field to a single-SEQUENCE encoding (probed live against
  `ldapmodify -e preread`: OpenLDAP does not honor the SEQUENCE-OF wrapper).
- `3876.2.1` (matched values): previously verified only resultCode 0 — the search
  used a malformed present filter (`87 00`, empty attribute) and returned no
  entries, so the assertion was vacuously passing. Now uses a real
  `(objectClass=*)` filter and verifies the returned description values are
  exactly the matching one (flat equalityMatch encoding, probed live against
  `ldapsearch -E mv=...`).
- `4529.3.1` (`@objectclass`): previously verified only resultCode 0 (same vacuous
  filter bug). Now uses the correct present filter and requires the returned
  attribute set to include cn and sn.
- Corpus links: `4511:4.1.1:2` (parseable-but-invalid → protocolError) now also
  links `4511.4.2.7` (bad version → protocolError), which is the actual
  parseable-but-invalid probe; the malformed-bytes assertion it was only linked
  to tests the *unparseable* branch. `2696:3:1` (paged results accepted + page +
  cookie) now also links `2696.2.2`, which verifies the cookie semantics that
  `2696.2.1` (acceptance only) does not.

## PARTIAL candidates (v2.2 PARTIALLY_COVERED ontology)

Recorded for the v2.2 coverage work; the assertion exercises part of the
requirement and the rest is genuinely hard or unexercised:

- `3829:4:1` — the authzId response control VALUE and the anonymous-empty branch
  are not verified (OpenLDAP does not implement the control; the ldap3 bind
  result does not expose the control value on 389 DS either). Current behavior
  (NOT_APPLICABLE / presence-only) is honest.
- `4511:4.2:9` — re-bind success is verified; the *new identity* being in effect
  is not (would need a Who-Am-I value check on the re-bound session).
- `3673:2:1` — "requesting '+' MUST return ALL operational attributes" is checked
  as "at least one operational attribute present"; enumerating all is not
  portable.
- `4513:3:4` — a client-side SHOULD (client refreshes capabilities after TLS)
  tested via server advertisement observation; attribution is questionable.
- `4511:4.1.1.1:2` — messageID 0 reserved for unsolicited notifications is
  checked via a robustness proxy (a request using 0 must not crash the server);
  the server-to-client unsolicited-notification path is not triggerable.
- `4527:3:1` / `4527:3:2` — the response control presence is verified; the
  returned entry's CONTENT (pre-update value / post-update value) is not parsed
  (a SearchResultEntry-in-control parser is needed).
- `4528:3:3` — the assertion control is exercised on Delete only; Add / Modify /
  ModifyDN are not.
- `4528:3:4` — resultCode assertionFailed verified; "and no entries returned" is
  not checked.
- `2891:2:3` — code is strict (sortResult must be 16); the "or the deviation the
  server reports" phrasing in the observables text is looser than the code and
  should be tightened (cosmetic).
- `3045:2:1` / `3045:2:2` — the NO-USER-MODIFICATION check is enforced via a
  root-DSE modify attempt; the schema declaration (attributeTypes entry) is not
  inspected.

## Genuine server findings surfaced by the strengthened assertions

- 389 DS does not implement RFC 4529 `@objectclass` attribute selection: a search
  requesting `@person` succeeds but returns no attributes (verified with 389 DS's
  own ldapsearch CLI). `4529.3.1` now FAILs on 389 DS. OpenLDAP passes.
- 389 DS does not advertise the matched-values control (RFC 3876); a critical
  matched-values control returns unavailableCriticalExtension, so `3876.2.1` is
  NOT_APPLICABLE there. OpenLDAP advertises and correctly filters values.
- OpenLDAP requires a non-empty AttributeSelection in the Pre/Post-Read request
  control (an empty selection yields strongAuthRequired rather than a response
  control); both targets honor the single-SEQUENCE controls encoding that
  `ldapmodify`/`ldapsearch` produce.

## Residual risks

- The SearchResultEntry parser added to `bauble.raw` (parse_search_entries /
  parse_search_response) is exercised by 3876.2.1, 4529.3.1/3.2 and unit tests;
  it assumes definite-length BER throughout (true for OpenLDAP and 389 DS).
- `4529.3.1`'s cn/sn check is a minimum (person's MUST attributes); a fuller check
  would verify the returned set equals the object class's MUST/MAY/SUP exactly.
