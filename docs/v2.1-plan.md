# v2.1 Plan — Coverage Fidelity and Growth

Response to the external review of the v2.0.0 release. The review validated
the architecture ("the first version I'd describe as a real conformance
framework without qualification") and shifted the danger: the question is no
longer "is this a test suite or a framework?" but **"does each assertion
faithfully cover the normative requirement it claims to cover?"**

The review's one forward-looking suggestion was a coverage ontology with
`UNCOVERED / COVERED / PARTIALLY_COVERED`, on the grounds that one assertion
can exercise only one obligation of a requirement containing several
independently-testable obligations. The review also advised not rushing that
until the corpus stabilizes.

This plan does three things, in order: audit assertion fidelity (the
stabilization), then introduce the coverage ontology, then grow coverage
against the stabilized corpus.

## Phase 1 — Assertion-fidelity audit (stabilize the corpus)

For each of the 128 requirements, verify that its `covered_by` assertion(s)
actually exercise the full normative statement — not part of it, and not an
adjacent behavior. This is the same pass that caught the 4516 → 4512
`supportedLDAPVersion` misattribution; expect more of the same classes:

- assertion attached to the wrong RFC (misattribution),
- requirement interpreted incorrectly by the assertion,
- assertion that assumes something non-normative,
- multiple requirements conflated into one assertion,
- a requirement with conditions the assertion ignores.

Output: a list of requirements whose assertions under-cover or mis-cover.
Under-covered requirements become the `PARTIALLY_COVERED` candidates in
Phase 2; mis-covered ones get fixed (attribution or assertion).

Prerequisite: none. This is read-only against the corpus.

## Phase 2 — PARTIALLY_COVERED coverage ontology

Extend the corpus so a requirement can be partially covered.

Data model: each requirement gains an explicit list of independently-testable
obligations; each obligation carries its own `covered_by`. A requirement is:

- **COVERED** — every obligation has at least one covering assertion,
- **PARTIALLY_COVERED** — some obligations have a covering assertion,
- **UNCOVERED** — no obligation has one.

Mechanics:

1. Corpus schema: `[[requirement]]` gains `obligations` (nested entries with
   their own `covered_by`). The existing top-level `covered_by` is the
   "all obligations" shorthand for single-obligation requirements.
2. Loader + `coverage_text`: report the three states per RFC, and list
   PARTIALLY_COVERED requirements with the uncovered obligations.
3. Reporters (summary) gain a partial-coverage rollup.
4. Seed: split the Phase-1 under-covered requirements into obligations.
   Single-obligation requirements are unchanged.

Sequencing: only after Phase 1, so the obligation split is grounded in the
fidelity audit rather than a mechanical re-read.

## Phase 3 — Coverage growth

Add assertions against the stabilized corpus. Concrete targets, grounded in
the current state (108/128 covered, 84%):

1. **SHOULD-advertise checks (8 requirements, ~8 assertions).** The existing
   advertise-check pattern (3829.2.1, 3876.7.1: read root DSE
   `supportedControl`/`supportedExtension`/`supportedFeatures`, PASS if
   present, UNTESTABLE/NA if absent) extends directly to:
   `2696:3:3` (paged), `2891:2:2` (sort), `3062:3:2` (passwdModify),
   `3866:4:1` (language tags/ranges), `4512:3:2` (operational attrs —
   creatorsName/createTimestamp), `4527:3:3` (read-entry), `4529:3:3`
   (object-class lists), `4532:3:2` (whoami). Coverage 108 → ~116.
2. **389 DS-specific findings (investigate, then either document or assert).**
   The suite surfaces genuine 389 DS divergence; decide per finding whether it
   is a documented server deviation (keep the FAIL, it is the finding) or an
   opportunity for a sharper assertion:
   - RFC 4526 empty filters rejected (protocolError) — 389 DS does not
     implement absolute true/false filters.
   - RFC 4511 §4.2 unknown auth choice → protocolError, not
     authMethodNotSupported.
   - RFC 5020 entryDN not implemented.
   - 4517 matching-rule behavior (caseIgnoreMatch, integerMatch ordering).
   - 3866 language-range matching.
3. **Intrinsic class-B gaps (10)**: atomicity, uniqueness, client-side
   requirements. Verify each is genuinely untestable and record the reason on
   the requirement (they should surface as UNTESTABLE with a reason, not as
   silent gaps).

## Non-goals

- No new test targets (ApacheDS, LLDAP) — independent, later.
- No dedicated Security profile.
- No machine-readable RFC corpus beyond the current per-RFC TOML (the
  obligations extension is additive, not a format change).
- PARTIALLY_COVERED is not rushed ahead of Phase 1.

## Definition of done

- Phase 1: audit report committed; every mis-cover fixed or explicitly
  accepted; under-covered requirements listed.
- Phase 2: `bauble coverage` reports the three states; corpus schema +
  loader + reporters + tests updated; under-covered requirements split.
- Phase 3: 8 advertise assertions landed and live-verified on both targets;
  389 DS findings either documented or asserted; intrinsic gaps carry
  reasons.
