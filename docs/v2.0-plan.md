# v2.0 Plan — Three-Layer Conformance Architecture

> Historical planning document for the v2.0.0 release (shipped). Where the
> plan and the shipped implementation differ — notably the requirements
> corpus, added in v2.0.0 — the shipped code and design notes are
> authoritative.

Turn bauble from an LDAP test suite into an LDAP specification
conformance framework. This is a major-version change because it requires
a systematic RFC re-read and a semantic model of what each requirement
actually asserts, not just new tests.

## Why 2.0

The current assertion model is excellent for traceability (RFC → section →
requirement → test → result). But it treats every assertion the same way.
A wire-format test, a filter-evaluation test, and a capability check all
live in the same flat registry.

The three layers formalize *what kind of conformance* each assertion
establishes:

| Layer | Question | Evidence |
|-------|----------|----------|
| **Wire** | Did the server correctly encode/decode protocol units? | resultCode, BER round-trip, PDU structure |
| **Semantic** | Does the operation produce the RFC-specified meaning? | DIT state, returned data, matching behavior |
| **Capability** | Does the server implement what it claims? | advertisement vs. behavior |

## Layer 1 — Wire conformance

**Question:** Can the server decode valid LDAPMessage BER, reject invalid
BER, enforce messageID semantics, encode responses correctly, handle
protocol operations/controls/extended ops/criticality, and return correct
result codes?

**Current coverage:** Partial. The raw wire layer (`src/bauble/raw.py`)
already handles BER malformation, bad protocol versions, empty-password
binds, and control-value BER. But there is no systematic wire-conformance
sweep.

**Work needed:**

1. Read RFC 4511 §4.1 (LDAPMessage, BER) and §5.1 (PDU definition)
   exhaustively. Extract every MUST about encoding.
2. Add assertions for:
   - messageID uniqueness/echoing in responses
   - BER definite-length enforcement
   - INTEGER / ENUMERATED / BOOLEAN encoding correctness
   - empty SEQUENCE handling
   - controls position (must be after protocolOp)
   - unknown critical control → `unavailableCriticalExtension`
   - unknown non-critical control → ignored
   - malformed filter → `ldapError`/protocolError
   - truncated PDU → connection close without crash
3. Tag each wire assertion `layer = WIRE`.

## Layer 2 — Semantic conformance

**Question:** Does `Search(base, scope, filter, attrs)` actually produce
the semantics specified by RFC 4511/4512/4517?

**Current coverage:** Partial and incidental. Filter evaluation (4515),
matching rules (4517/4518), and schema (4519) have assertions, but they are
organized by RFC, not by semantic concern.

**Work needed:**

1. Read RFC 4511 §4.5 (Search), RFC 4512 §4.1 (filters), RFC 4517
   (matching rules), RFC 4518 (string prep) for semantics.
2. Add assertions for:
   - DN comparison (case-insensitive attribute names, case-sensitive values)
   - filter evaluation: AND/OR/NOT/equality/substring/present/extensible
   - matching rules: caseIgnore, caseExact, distinguishedName, integer,
     generalizedTime
   - schema constraints: objectClass MUST/MAY, single-value enforcement,
     attribute syntax validation
   - modification semantics: add/delete/replace/increment behavior
   - ModifyDN semantics: leaf rename, subtree rename, newSuperior
   - alias dereferencing
   - referral handling
3. Tag each semantic assertion `layer = SEMANTIC`.

## Layer 3 — Capability conformance

**Question:** Does the server correctly implement what it claims to
implement?

**Current coverage:** The advertise-then-test pattern (v1.1.0) is exactly
this, but it's implemented ad-hoc per assertion.

**Work needed:**

1. Formalize the pattern. Add a `Layer` enum to the model; classify every
   existing assertion.
2. For every feature OID in the registry (supportedControl,
   supportedExtension, supportedFeatures), assert:
   - advertised + behavior correct → CONFORMANT
   - advertised + behavior wrong → FAIL (implementation bug)
   - not advertised + behavior irrelevant → NOT_APPLICABLE
3. The conformance report gains a per-capability table:

   ```text
   OID             Advertised  Exercised  Verdict
   1.3.6.1.1.12    YES         FAIL       "advertised but not processed"
   ```

## Data model changes

Add to `Assertion`:

```text
layer: Layer          # WIRE | SEMANTIC | CAPABILITY
```

Add `Layer` enum to `model.py`. Every assertion gets a `layer` tag.
The registry remains flat; `layer` is a query dimension like `profile`
and `category`.

Reporters gain a per-layer rollup in the summary:

```text
Wire:       18/20 PASS, 2 UNTESTABLE
Semantic:   21/25 PASS, 3 FAIL, 1 UNTESTABLE
Capability:  9/12 PASS, 1 FAIL, 2 NOT_APPLICABLE
```

## RFC re-read scope

The three-layer classification requires re-reading these RFCs with
explicit attention to layer:

| RFC | Layer focus |
|-----|-------------|
| 4511 §4.1 | Wire (BER, LDAPMessage, controls) |
| 4511 §4.2-4.14 | Semantic (operations), Wire (PDU encodings) |
| 4512 | Semantic (information model) |
| 4513 | Semantic (auth), Wire (SASL exchange) |
| 4514-4518 | Semantic (string/filter/matching rules) |
| 4519 | Semantic (schema) |
| 2696/2891/3062/3829/3866/3876/4525/4526/4527/4528/4529/4530/4532/5020/6171 | Capability + Semantic |

## Migration path

This is not a rewrite. It is a reclassification plus targeted additions.

1. Add `Layer` enum and `layer` field (v2.0.0).
2. Reclassify all 100+ existing assertions. Most are already correct;
   only the tag is missing.
3. Add the wire-conformance sweep (Layer 1) — the largest new work.
4. Add semantic gaps identified in the re-read (Layer 2).
5. Formalize capability reporting (Layer 3).
6. Update reporters, docs, conformance matrix.

## What is NOT in v2.0

- The requirements corpus (TOML spec files per RFC) was originally deferred
  here but was added in v2.0.0; see docs/design-notes.md "Requirements corpus
  and coverage".
- A dedicated Security profile — separate concern, may be v2.1.
- More test targets (ApacheDS, LLDAP) — independent, can be v2.1.

## Versioning

v2.0.0 = three-layer architecture + reclassification + wire sweep.
Subsequent minor versions add semantic coverage and targets.
